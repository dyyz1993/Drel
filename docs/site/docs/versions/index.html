Versions and Contract Policy

Read versions from window.DrelRuntime at runtime and feature-detect individual fields. Never assume a future Drel release grants a remote page new native powers.

Current public contract

Each surface carries its own version number. They move independently, so read them separately at runtime.

SurfaceVersionRead it fromMeaning
Drel app 1.5.x App Store version / CFBundleShortVersionString Push, HTTPS container, registered apps, and the Manifest v2 action runtime.
Container protocol containerVersion: 1 window.DrelRuntime.containerVersion Versioned UA product token and the DrelRuntime environment object.
Offline package protocol offlinePackageVersion: 1 window.DrelRuntime.offlinePackageVersion Hash-verified, atomically activated package support.
Native actions bridgeVersion: 2 window.DrelRuntime.bridgeVersion Manifest v2 declared actions. 1 is the legacy bridge surface; 0 means no native surface at all.
Agent skill 1.1 The skill's own version The version of the contract bundle handed to an AI agent.
Version 0 is not "old", it is "closed". A bridgeVersion of 0 means the container exposes no native command surface. The Store build reached 2 in Drel 1.5.0; earlier 1.4.x builds expose 0.

App version to capability map

Drel appcontainerVersionofflinePackageVersionbridgeVersionYou get
1.4.x 1 1 0 Push, HTTPS container, registered apps, strong offline packages, deep links. No native action surface.
1.5.x 1 1 2 Everything in 1.4.x, plus declared native actions, the permission center, and the grant ledger.

How to read the version at runtime

const runtime = window.DrelRuntime;

const hasContainer   = Number(runtime?.containerVersion ?? 0) >= 1;
const hasOffline     = Number(runtime?.offlinePackageVersion ?? 0) >= 1;
const hasNativeOps   = Number(runtime?.bridgeVersion ?? 0) >= 2;
const isOfflinePkg   = runtime?.isOfflinePackage === true;

Feature-detect each capability separately. A page must keep working in a plain browser, so treat every one of these as an enhancement rather than a requirement.

Compatibility rules

  • Minor app updates may add optional fields. Integrations must ignore unknown fields and tolerate missing optional fields.
  • A documented stable field is not silently redefined. If a breaking change is necessary, it receives a new versioned contract or a formal deprecation period.
  • Undocumented endpoints, aliases, and experimental fields have no compatibility promise.
  • The app marketing version is not an authorization level. A page must still feature-detect, validate data, and use ordinary web fallbacks.

How a release ships

Every build you can install passed the same gates. Local checks archive their evidence whether they pass or fail; publishing requires a recorded human approval, not the absence of an objection. The edge worker deploys automatically through CI, while TestFlight, this site, and self-hosted servers publish manually — and every layer keeps a rollback path.

Self-hosting status

Self-hosting documentation is separate because a stock Drel install and a deployment with an authorized APNs signer have different responsibilities. Read the Self-host Drel Guide before planning deployment. Never paste a private APNs signing key into a public repository or client QR code.
